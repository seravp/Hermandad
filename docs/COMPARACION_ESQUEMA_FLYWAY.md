# Comparación de producción con Flyway V1

## Dictamen

El esquema aportado es compatible con las entidades actuales y con el baseline explícito en versión 1. V1 se ha corregido para reproducirlo. No se ha conectado a producción ni desplegado nada.

La conclusión se refiere al archivo `D:\dev\hermandad\backend\produccion_schema.sql`, no a una inspección en vivo. Antes de ejecutar el baseline real hay que confirmar que el volcado sigue vigente, el destino/esquema es el correcto, no existe un historial Flyway previo y se dispone de backup completo cuya restauración esté probada. El volcado solo contiene estructura: no permite certificar datos reales, valores actuales de secuencias, propietarios, permisos o configuración del servidor.

## Método y evidencia

Se restauró el SQL aportado en una base PostgreSQL temporal. En bases separadas se ejecutaron la V1 anterior y la V1 corregida; esta última mediante Flyway. Se compararon catálogos y exports `pg_dump --schema-only --no-owner --no-privileges` producidos por el mismo servidor/cliente. Se excluyó únicamente la tabla de historial añadida por Flyway. Los exports finales son idénticos tras retirar las dos líneas de tokens aleatorios `\restrict`/`\unrestrict`; no se eliminaron diferencias de DDL para conseguir ese resultado.

Producción según cabecera: PostgreSQL 18.6 Ubuntu. Validación local: PostgreSQL 18.4 Windows (misma versión principal, distinta revisión y plataforma). No se ha certificado la configuración regional ni la collation efectiva del servidor real.

Los catálogos comparados incluyen orden de columnas, tipos completos, nulabilidad, identidad, columnas generadas, defaults, collation declarada, almacenamiento/compresión, comentarios, restricciones y su validación/diferibilidad, índices, secuencias y propiedad de sus columnas, persistencia, método de acceso, tablespace, RLS y replica identity. Se revisó el volcado entero para otros objetos.

## Diferencias encontradas en la V1 anterior

1. **Diferencia funcional:** `socios.nombre`, `socios.apellidos` y `socios.dni` admitían NULL; producción exige NOT NULL. Se corrigieron las tres columnas. Las entidades exigen esos campos con `@NotBlank`, por lo que producción es coherente con el modelo. Los datos ficticios de los tests se ajustaron y se añadió una prueba que comprueba que las tres inserciones con NULL se rechazan. Hibernate `validate` por sí solo no había detectado esta diferencia.
2. **Orden de columnas:** era distinto en las nueve tablas. Se igualó al volcado, aunque JPA usa nombres de columnas. Esto también evita diferencias en `SELECT *`, COPY e inserciones posicionales.
3. **Nombres:** cinco UNIQUE y tres FK tenían nombres autogenerados distintos. Los cinco índices que respaldan esos UNIQUE también diferían de nombre. Se conservaron los nombres de producción para que futuras migraciones puedan referirse a ellos igual en ambos entornos. No cambiaron columnas ni semántica.
4. **CHECK:** permitían exactamente los mismos valores, pero el parser de PostgreSQL generaba árboles de casts diferentes al restaurar el dump y al ejecutar los `IN` simples. V1 ahora utiliza casts SQL explícitos equivalentes; el catálogo final coincide también textualmente. H2 admite la misma migración.
5. No había diferencias en tablas/columnas presentes, tipos, longitudes, precisión/escala, PK, acciones FK, conjuntos de valores CHECK, semántica UNIQUE, parámetros/propiedad de secuencias o defaults, aparte de las tres nulabilidades indicadas.

## Otros objetos y compatibilidad con las entidades

- Las nueve tablas son permanentes, método heap, sin particiones/herencia, opciones de almacenamiento específicas, tablespace explícito, comentarios, RLS activado ni replica identity especial.
- El dump no contiene vistas, vistas materializadas, rutinas, triggers de usuario, políticas, tipos enum/domain propios, extensiones declaradas, reglas, grants, cambios de propietario o ajustes de privilegios por defecto. Los triggers internos que implementan FK se crean normalmente al restaurarlas.
- `public` es el esquema de todos los objetos. V1 usa nombres sin prefijo para funcionar también en los esquemas aislados de test; con el esquema Flyway `public`, como en producción, los objetos son idénticos. No cambiar el esquema efectivo al adoptar.
- Todos los enums Java coinciden con los nueve CHECK; se almacenan como varchar, no como tipos enum nativos.
- Coinciden el mapeo de las nueve entidades, sus relaciones, campos obligatorios, longitudes 9/34/120/255/2000, importes numeric(38,2), valor de inventario numeric(12,2), fechas y timestamps(6) sin zona horaria, y las ocho identidades. No fue necesario modificar entidades.
- NOT NULL no equivale a validar cadenas en blanco, DNI de exactamente nueve caracteres, correo o IBAN: esas validaciones siguen en la aplicación. No se han añadido CHECK nuevos que producción no tenga.
- No hay UNIQUE de DNI en el dump ni en la entidad; el servicio comprueba duplicados. No se añade aquí: sería otro cambio funcional.
- Al no figurar propietarios/ACL en el dump, la igualdad de las restauraciones no certifica privilegios del usuario real. Tampoco certifica locales, configuración de base/servidor o contenido ajeno al alcance del volcado.
